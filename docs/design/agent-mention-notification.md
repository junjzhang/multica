# 智能体提及：委派与只通知

状态：提案，待用户确认。代码基线：`748168026c`（`feat/task-session-delivery`）；本稿只设计，不改变行为。

## 现状与问题

- **事实**：解析器以类型和 ID 去重，当前智能体语法是 `[@名称](mention://agent/<uuid>)`（`server/internal/util/mention.go:11`、`:23`）。评论触发可执行运行时，Agent 作者的地址先验证，再在评论事务中记录及关联（`server/internal/handler/delegation_return.go:61`、`:111`；创建和编辑入口见 `server/internal/handler/comment.go:1879`、`:3529`）。并非每个提及都一定建关系：阻止的目标、成员作者等有现有例外。
- **事实**：评论关联是重放、折叠和重触发的持久意图；运行保存的回投集合用于结果通知，重试会复制它（`server/pkg/db/queries/delegation_return.sql:49`、`:144`、`:176`）。session-tasks 的已委派列表按 current return 和相关运行投影（`server/pkg/db/queries/session_tasks.sql:75`）。
- **推断**：用委派语法提醒时，提醒者可能成为持久回投方；只改面板显示无法消除后续结果投递。

## 推荐：每个目标显式声明

- 保留现有 `mention://agent/<uuid>` 为**委派**；新增 `mention://agent-notify/<uuid>` 为**只通知**。两者都沿用同一访问、运行时和触发检查；通知表示请求对方查看/处理，可唤醒，并非静默抄送。编辑器选择目标时显式选择“委派”或“只通知”，在正文和已发布评论中可辨识；CLI 支持同一规范语法。API 保存的内容本身是权威意图，预览、提交和编辑必须一致。
- 候选比较：评论级标志无法在一条评论内混合目标，且复制正文会丢语义；仅 CLI/GUI 选项若不持久编码会在重放和旧客户端丢失；按作者、负责人或上下文推断会误判。语法变体允许逐目标混合和审计，但需要升级解析、渲染和所有入口。
- 同一目标重复同一模式去重；同一评论对同一目标同时出现两种模式时拒绝提交并指明冲突，不静默选择一种。`@squad` 和成员提及不变；通知语法只针对 Agent。对编辑：未执行的意图可按新版本重新计划；已经接受的委派不可通过编辑撤销或改写，已触发的通知也不重复启动。删除、重放、重试按保存的版本和既有幂等规则处理，不能把历史通知重新解释为委派。
- **兼容**：旧语法继续委派，避免旧客户端的工作请求丢失回投。新服务先发布解析、持久化和渲染，再启用新客户端；旧客户端必须可见地呈现“只通知”而非误显示为普通委派，无法保证时禁用其编辑/发送入口。新客户端对不支持的服务禁止发送该模式并提示升级，不能降级成旧语法；服务端须对未知或畸形模式拒绝，而非保存为无声文本。能力协商和版本覆盖需实施时明确。

## 运行、结果和消费者

- 每个触发意图持久化模式、评论版本、目标及来源，原子写入评论与入队；通知跳过该作者的地址准备、`Ensure` 和评论回投链接，不创建、替换或退休任何 current return。重放、恢复及外部 Mailbox 使用同一持久意图，不能从自由文本或当前任务关系重新猜测。
- 通知触发的运行上下文明确标示“只通知”、来源评论及目标；它仍遵守该任务原有合同、权限和执行者职责。结果按现有规则写任务评论；**不因本通知新增任何回投**。若运行本身已有其他已接受的委派关系，继续向这些冻结地址回投；不自动从任务所有 current return 推导原负责人，也不清除既有运行关系。通知单独启动且没有既有运行关系时无自动回投。回投和评论是独立事实。
- 并发/折叠：通知与委派合并到同一运行时保留每个来源及模式，仅委派贡献回投；通知不能移除或借用其他来源的关系。运行上下文展示全部来源，重试继承原运行已接受集合与来源；若现有队列无法可靠表达混合意图，拒绝/排队而非降级。避免把通知归因成委派或因通知抑制已接受结果。
- session-tasks：“我派出去的”仅基于真实委派运行，通知不新增该项；已有条目不受影响。核对待答请求投影（`server/pkg/db/queries/session_tasks.sql:107`），区分通知与请求，避免将通知误列为待答委派。Mailbox 对外部目标仍交付唤醒请求，载荷带模式并保持去重及回执；不为通知创建结果回投 Mailbox。wakeup 是独立触发机制，既有定时/条件及来源身份不变；由 wakeup 发出的评论按明确语法处理，不改变 wakeup 的回执与续接。
- squad：直接通知队长不自动变成 `@squad`、不获得队长上下文或改变领导关系；已有 `@squad` 升级与合并规则需保留（`server/internal/handler/comment.go:3118`）。Contract 的 executor、acceptor、submit 和验收权限不由通知改变。`trigger_outcomes` 继续报告每个目标实际 queued、coalesced、blocked 等结果（`server/internal/handler/comment.go:83`、`:2502`），增加可兼容的模式字段；投递成功不代表已处理或验收。

## 存量清理

- 推荐独立的人类“撤销未来回投关系”入口，展示任务、分发者、冻结地址、来源、受影响的未完成运行与已保存结果；人类核对后逐条确认，记录操作者、原因和时间，使用版本/CAS 与权限校验，并发变化时要求重新确认。不得按提及文本、关系数量或时间自动判断误建；无法证明为提醒的关系由人判断。
- 现有结果接管面向指定的已保存终态和替代目标，且要求人类操作（`server/internal/handler/result_takeover.go:65`、`:344`），不是无目标撤销。复用其权限、锁和审计设计，不直接复用其动作。撤销只阻止明确选定关系的**未来**关联；已接受运行及已物化/在途结果保持冻结，不删除历史、不撤回已发送内容。若用户要停止已有未完成义务或改接收人，另走明确接管/后续专项设计，不能假称撤销已解决。先预览影响再实施；本设计不操作 WORK-266 数据。

## 验收计划与范围

- 解析及客户端：同一目标重复、混合冲突、多个目标、无效 ID、编辑与复制、旧/新服务能力及各客户端渲染；旧语法与旧客户端回归。
- 服务与持久化：通知成功/blocked、访问拒绝、事务失败、创建/编辑/删除、重放和崩溃恢复；验证无新增或改写 return，委派行为不变。覆盖通知与委派并发合并、重试和既有冻结地址，逐个检查运行上下文、结果评论、实际投递及去重。
- 消费者：session-tasks、外部和托管 Mailbox、wakeup、squad、Contract、`trigger_outcomes`；验证模式和回执，不把入队当成完成。清理入口覆盖授权、预览、CAS 冲突、审计和已物化/在途结果不变。
- 不做：本 PR 不实现、不迁移或清理生产数据，不改变默认委派、合同责任、成员/小队语义或撤回已投递结果。
