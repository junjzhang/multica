# 智能体提及：委派与只通知

状态：用户已定案，实施中。代码基线：`748168026c`（`feat/task-session-delivery`）；本稿记录本次实现的目标语义。

## 现状与问题

- **事实**：解析器以类型和 ID 去重，当前智能体语法是 `[@名称](mention://agent/<uuid>)`（`server/internal/util/mention.go:11`、`:23`）。评论触发可执行运行时，Agent 作者的地址先验证，再在评论事务中记录及关联（`server/internal/handler/delegation_return.go:61`、`:111`；创建和编辑入口见 `server/internal/handler/comment.go:1879`、`:3529`）。并非每个提及都一定建关系：阻止的目标、成员作者等有现有例外。
- **事实**：评论关联是重放、折叠和重触发的持久意图；运行保存的回投集合用于结果通知，重试会复制它（`server/pkg/db/queries/delegation_return.sql:49`、`:144`、`:176`）。session-tasks 的已委派列表按 current return 和相关运行投影（`server/pkg/db/queries/session_tasks.sql:75`）。
- **推断**：用委派语法提醒时，提醒者可能成为持久回投方；只改面板显示无法消除后续结果投递。

## 推荐：每个目标显式声明

- 保留现有 `mention://agent/<uuid>` 为**委派**；新增 `mention://agent-notify/<uuid>` 为**只通知**。两者都沿用同一访问、运行时和触发检查；通知表示请求对方查看/处理，可唤醒，并非静默抄送。编辑器选择目标时显式选择“委派”或“只通知”，在正文和已发布评论中可辨识；CLI 支持同一规范语法。API 保存的内容本身是权威意图，预览、提交和编辑必须一致。
- 候选比较：评论级标志无法在一条评论内混合目标，且复制正文会丢语义；仅 CLI/GUI 选项若不持久编码会在重放和旧客户端丢失；按作者、负责人或上下文推断会误判。语法变体允许逐目标混合和审计，但需要升级解析、渲染和所有入口。
- 同一目标重复同一模式去重；同一评论对同一目标同时出现两种模式时按委派处理，委派包含唤醒。`@squad` 和成员提及不变；通知语法只针对 Agent。编辑沿用现有取消并重新规划语义：内容变化时清除评论关联、取消该评论触发任务并重新规划（`server/internal/handler/comment.go:3607`、`:3618`）。通知改委派时新计划接受回投；委派改通知时新计划不新增回投，但已冻结的运行结果和历史按现有生命周期处理。删除、重放、重试使用持久化的触发意图和既有幂等规则。
- **兼容**：旧语法继续委派；旧客户端只接受降级显示，不做编辑保护或能力协商。Web、桌面、插件和 CLI 同次发布一起升级。旧服务不识别通知语法，部署前不发送。

## 运行、结果和消费者

- 每个触发意图持久化模式、目标及来源，原子写入评论与入队；通知跳过该作者的地址准备、`Ensure` 和评论回投链接，不创建、替换或退休任何 current return。obligation 的创建须按可执行触发目标决定，不再以作者地址非空为开关（`server/internal/handler/comment.go:1900`、`:3541`）；通知目标的 `delegation_return_id` 为空，保证纯通知及委派改通知的崩溃恢复。现有评论回投关联仅按评论而非目标（`server/migrations/618_issue_delegation_return.up.sql:56`），因此须按目标关联回投或在 obligation 上持久化等价的目标意图；新运行、折叠、补偿入队、编辑 obligation（`server/internal/handler/comment.go:2336`、`:2733`、`:2870`、`:3556`）全部按目标取集合，通知目标贡献空集合。重放、恢复及外部 Mailbox 使用同一持久意图，不能从自由文本或当前任务关系重新猜测。
- 通知触发的运行上下文明确标示“只通知”、来源评论及目标；它仍遵守该任务原有合同、权限和执行者职责。结果按现有规则写任务评论；**不因本通知新增任何回投**。若运行本身已有其他已接受的委派关系，继续向这些冻结地址回投；不自动从任务所有 current return 推导原负责人，也不清除既有运行关系。通知单独启动且没有既有运行关系时无自动回投。回投和评论是独立事实。
- 并发/折叠：通知与委派合并到同一运行时保留每个来源及模式，仅委派贡献回投；通知不能移除或借用其他来源的关系。运行上下文展示全部来源，重试继承原运行已接受集合与来源；若现有队列无法可靠表达混合意图，拒绝/排队而非降级。避免把通知归因成委派或因通知抑制已接受结果。
- session-tasks：“我派出去的”仅基于真实委派运行，通知不新增该项；已有条目不受影响。核对待答请求投影（`server/pkg/db/queries/session_tasks.sql:107`），通知不列为待答请求；若用户需要对方必须回复，应选择委派。Mailbox 对外部目标仍交付唤醒请求，载荷带接受时的模式并保持去重及回执；不为通知创建结果回投 Mailbox。外部投递沿用现有不可变载荷与编辑不重投行为：编辑已投递评论不会改变原投递模式，也不会产生新投递；需要新的外部动作时发新评论。wakeup 是独立触发机制，既有定时/条件及来源身份不变；由 wakeup 发出的评论按明确语法处理，不改变 wakeup 的回执与续接。
- 入口需同步识别新类型：会话冲突门禁（`server/internal/handler/external_session_scope.go:96`）、触发判断（`server/internal/handler/comment.go:3068`、`server/internal/handler/squad.go:1265`）、解析器、移动端序列化/渲染，以及运行时说明和内置 skills（`server/internal/daemon/execenv/runtime_config_sections.go:722`）。冲突必须有明确拒绝/回执，不能保存后无声漏触发。
- squad：直接通知队长不自动变成 `@squad`、不获得队长上下文或改变领导关系；已有 `@squad` 升级与合并规则需保留（`server/internal/handler/comment.go:3118`）；同一评论委派小队并通知其队长时按小队委派建立运行和回投，两个目标的回执各保留自身模式。Contract 的 executor、acceptor、submit 和验收权限不由通知改变。`trigger_outcomes` 继续报告每个目标实际 queued、coalesced、blocked 等结果（`server/internal/handler/comment.go:83`、`:2502`），增加可兼容的模式字段；投递成功不代表已处理或验收。

## 验收计划与范围

- 解析及客户端：同一目标重复、混合优先级、多个目标、无效 ID、编辑与复制、旧/新服务兼容及各客户端渲染；旧语法与旧客户端回归。
- 服务与持久化：通知成功/blocked、访问拒绝、事务失败、创建/编辑/删除、重放和崩溃恢复；验证无新增或改写 return，委派行为不变。具名回归：同评论委派 A、通知 B，在新运行、折叠、obligation 重放中 B 不继承 A 的回投；通知与委派互改；会话冲突时通知明确失败；`@squad` 加队长通知合并；重试和既有冻结地址逐个检查运行上下文、结果评论、实际投递及去重。
- 消费者：session-tasks、外部和托管 Mailbox、wakeup、squad、Contract、`trigger_outcomes`；验证模式和回执，不把入队当成完成。
- 不做：本 PR 不迁移或清理生产数据，不改变默认委派、合同责任、成员/小队语义或撤回已投递结果。
