---

明确 @是交接信号。在评论中 @智能体，适合让它查看一条新信息、回答问题或协助当前负责人。评论会成为这次执行的起点，任务的负责人和状态都不会改变。

不带明确 @的普通评论或回复只是讨论，不会启动负责人、讨论中的智能体或任何其他对象。

## 分配与 @提及的选择

| | 分配给智能体 | 在评论中 @智能体 |
|---|---|---|
| 适合 | 让智能体负责整条任务 | 请智能体处理当前评论 |
| 改变负责人 | 是 | 否 |
| 改变状态 | 否 | 否 |
| 一次选择 | 一个智能体或小队 | 可以 @多个智能体或小队 |
| 本轮焦点 | 整条任务 | 触发它的评论，以及同批合并的评论 |

需要明确负责人时使用[分配](/assigning-issues)；只需要临时加入讨论时使用 @提及。

## 触发预览

在评论编辑器中选择智能体或小队后，输入框下方会显示触发预览：

- 哪些智能体会在发送后开始工作；
- 目标是直接 @提及，还是小队 leader；
- 目标是否不可用，或你是否缺少调用权限。

取消选中某个智能体只跳过这一次触发，不需要删除评论中的名字，也不会修改智能体的 Access。

![发送前的触发预览：列出发送后将开始工作的智能体](/images/docs/mention-trigger-preview.webp)

评论发布后，在线的运行时通常立即领取；运行时离线时，运行留在队列中等待。

## 只有明确 @才会启动工作

回复智能体的评论、在它参与的讨论中回复，以及在它负责的任务下评论，都属于讨论，都不会启动运行。需要智能体参与时，请明确 @它，或把任务分配给它。

回复始终交给被明确 @的智能体，即使它的运行时离线或正在忙碌，也不会在超时后自动唤醒负责人。

## 连续评论的合并

同一个智能体在同一条任务上已有排队中的运行，此时对它的新明确 @提及会合并进这次运行；它已经在执行时，后续提及等当前运行结束后合并为一次跟进执行。可以连续补充信息，不必等智能体回复。

一条评论 @多个不同智能体时，每个智能体各得一次运行；多个提及指向同一个智能体时，只保留一次。

## 不会启动智能体的评论

没有明确 @提及的评论不会启动任何智能体。两种写法可以明确表达这个意图：

- 以 `/note` 开头：评论作为成员之间的备注。
- 使用 `@all`：通知全部工作区成员，不启动任何智能体。

触发预览中仍有智能体时，发送前取消选中即可。

<Callout type="info">
`@all` 不包含智能体。智能体没有收件箱；让它工作需要明确 @它，或把任务分配给它。
</Callout>

## 外部智能体与 mailbox

明确 @外部智能体（绑定到 Paseo 等宿主会话的智能体）时，请求会保存到该智能体的 mailbox。已登记的宿主适配器负责投递：空闲会话在原会话开始新一轮，忙碌会话在当前轮结束后再处理。Multica 不会打断会话，也不会创建替代会话。

首版只投递到 Paseo，并依赖单独提供的原子 if-idle 宿主扩展。没有该扩展的 Paseo 会返回可操作的依赖错误，请求继续排队；仅读取 mailbox 不会启动会话。请求已保存、已投递或已读，都不代表工作已经开始。

## Access 限制

@提及不能绕过智能体的 Access。无权调用、目标已归档、托管目标没有可用运行时，或外部宿主无法接收投递时，触发预览或评论的触发结果会说明它不会启动；评论本身仍可正常发布。三档语义见[智能体](/agents#权限与-access)。

## 智能体之间的互相提及

智能体可以在自己的回复中 @其他智能体。A @ B、B 又 @ A 时，系统会合并同一时刻的重复执行，但不会判断这段协作是否应该结束——协作的终止条件需要写进智能体指令。

执行者的结果需要 leader、协调者或下一位执行者处理时，必须在结果评论中明确 @对方。普通回复不会唤醒任何人。
